## 五、认识测试计划结构

JMeter GUI 左侧树结构：

```
FlashSale 秒杀压测计划              ← 根节点，可配变量 BASE_URL / GOODS_ID
├── HTTP 请求默认值                  ← 所有请求共用 localhost:8080
│
├── 01-登录获取Token (setUp线程组)    ← 【只在压测开始前运行一次】
│   ├── 用户数据CSV                   ← 读取 users.csv
│   ├── POST /api/user/login          ← 用 CSV 的账号密码登录
│   └── 提取Token                     ← 把返回的 Token 存为全局属性
│
├── 02-秒杀请求（主压测）             ← 【核心压测线程组】
│   ├── 随机取Token                   ← 每个线程拿到一个 Token
│   ├── POST /api/seckill/{goodsId}   ← 秒杀请求
│   ├── GET /api/order/result/{goodsId} ← 轮询秒杀结果
│   └── 间隔200ms                      ← 两次迭代之间等 200ms
│
├── 察看结果树                        ← 看每个请求的详情（调试用）
├── 聚合报告                          ← 最常用：TPS/平均/最大/错误率
├── 汇总报告                          ← 实时汇总
└── 图形结果                          ← 折线图
```

### 流程说明

```
压测开始
  │
  ├─ [setUp] 100 个线程先后登录，拿到 100 个 Token 存入内存
  │
  └─ [主压测] 200 个线程持续运行 60 秒
       │
       └─ 每个线程的死循环：
            ① 从 100 个 Token 里随机取一个
            ② POST /api/seckill/1  → 发起秒杀
            ③ 等 200ms
            ④ GET /api/order/result/1 → 轮询结果
            ⑤ 回到 ①
```

## 六、调整压测参数

### 6.1 调整并发强度

点击左侧 **"02-秒杀请求（主压测）"**，右侧面板修改：

| 参数 | 含义 | 建议值 |
|------|------|--------|
| Number of Threads | 并发用户数 | **先 50，再 200，最后 500** |
| Ramp-up Period | 逐步启动秒数 | 10 秒 |
| Duration | 持续总时长 | 60 秒 |

> Ramp-up = 10 表示：50 个线程在 10 秒内逐步启动（每秒启动 5 个），不是一下子全冲上去。这样更接近真实场景。

### 6.2 增加测试用户

只有 2 个用户的话，防重机制会让大量请求返回"请勿重复购买"。批量插入 500 个用户：

```sql
-- 在 Navicat/DataGrip 中执行（密码 123456，salt=1a2b3c4d）
INSERT INTO user (phone, password, salt, nickname)
SELECT
    CONCAT('138', LPAD(n, 8, '0')),
    'b7797c6b0187825e79db224b88c12831',
    '1a2b3c4d',
    CONCAT('压测用户', n)
FROM (
    SELECT @row := @row + 1 AS n
    FROM information_schema.columns, (SELECT @row := 2) r
    LIMIT 500
) t;
```

同时更新 `users.csv` 为其生成 500 条数据，或者直接用 BeanShell 脚本动态生成手机号（高级用法，不在此展开）。

如果不需要 500 个用户，也可以手动在 `users.csv` 加几条：

```csv
phone,password
13800000001,123456
13800000002,123456
```

> 压测时 "重复购买" 错误（code=500202）是正常的业务拒绝，不算系统异常。

### 6.3 修改秒杀商品 ID

点击根节点 **"FlashSale 秒杀压测计划"**，右侧变量列表：

| 变量 | 默认值 | 说明 |
|------|--------|------|
| BASE_URL | localhost:8080 | 后端地址 |
| GOODS_ID | 1 | 商品 ID（1/2/3） |

### 6.4 要不要改限流阈值

限流配置在 `RateLimitInterceptor.java` 中：

```java
private static final int MAX_COUNT = 5;   // 窗口内最多 5 次
private static final int WINDOW_SIZE = 5; // 窗口 5 秒
```

如果压测时大量请求被限流拒绝（code=500206），可以提高或干脆注释掉限流拦截器注册（`WebConfig.java` 中移除 `rateLimitInterceptor`）。

## 七、运行压测

### 7.1 GUI 模式（调试用）

点顶部绿色 **▶** 按钮。右上角会显示 `0/50 → 50/50`。

> 注意：GUI 模式本身吃内存，200+ 并发时建议用 CLI 模式。

### 7.2 CLI 模式（正式压测）

```bash
# 进入 jmeter 目录
cd D:\codeSpace\FlashSale\jmeter

# 清掉上次结果
del result.jtl
rmdir /s /q report

# 命令行运行
D:\jmeter\apache-jmeter-5.6.3\bin\jmeter -n -t flashsale-load-test.jmx -l result.jtl -e -o report/

# 查看 HTML 报告
start report\index.html
```

参数说明：

| 参数 | 含义 |
|------|------|
| `-n` | 非 GUI 模式 |
| `-t` | 测试计划文件 |
| `-l` | 原始结果保存为 .jtl |
| `-e -o report/` | 生成 HTML 报告到 report 目录 |

## 八、查看结果

### 8.1 聚合报告（GUI）

```
Label                         Samples  Average   Min  Max   Error%  Throughput
POST /api/seckill/1           3500     12ms      3    89    0.5%    58.3/sec
GET  /api/order/result/1      3500     3ms       1    18    0.0%    58.3/sec
TOTAL                         7000     7.5ms     1    89    0.25%   116.6/sec
```

关注：

| 指标 | 含义 | 好 | 坏 |
|------|------|-----|-----|
| **Throughput** | 每秒处理请求数（TPS） | >500 | <100 |
| **Average** | 平均响应时间 | <50ms | >500ms |
| **Error%** | 错误率 | <0.1% | >1% |
| **Min / Max** | 最快 / 最慢 | — | 差距过大说明不稳定 |

> Error% 中的"错误"指的 HTTP 异常或响应 code≠0。业务正常拒绝（已售罄/重复购买）的 code≠0，但不算系统错误。

### 8.2 察看结果树（调试用）

点开绿色请求 → Response Body，确认：

- `"code":0` → 秒杀成功排队
- `"code":500202` → 重复购买（业务拒绝）
- `"code":500203` → 已售罄（业务拒绝）
- `"code":500206` → 限流触发

### 8.3 HTML 报告（CLI 模式）

CLI 跑完后，`report/index.html` 提供了更丰富的图表：

- **Over Time** — TPS / 响应时间 随时间变化的曲线
- **Latency** — 百分位延迟（50%/90%/95%/99%）
- **Errors** — 每个接口的错误统计

## 九、验证数据正确性

### 9.1 不超卖

```sql
-- 库存初始 100，order_info 表行数不应超过 100
SELECT
    g.id,
    g.stock_count AS 初始库存,
    COUNT(o.id) AS 实际下单数,
    g.stock_count - COUNT(o.id) AS 剩余库存
FROM goods g
LEFT JOIN order_info o ON o.goods_id = g.id AND g.id = 1
WHERE g.id = 1
GROUP BY g.id;

-- 实际下单数 ≤ stock_count（100）→ 不超卖 ✅
```

### 9.2 防重

```sql
-- 同一个用户对同一个商品只能有 1 条记录（uk_user_goods 保证）
SELECT user_id, goods_id, COUNT(*) AS cnt
FROM seckill_order
GROUP BY user_id, goods_id
HAVING cnt > 1;

-- 应当返回空 → 防重生效 ✅
```

### 9.3 库存扣减一致性

```bash
# Redis 中的库存（压测后）
redis-cli GET seckill:stock:1

# DB 中的库存
mysql -uroot -p -e "SELECT stock_count FROM flashsale.goods WHERE id = 1"

# Redis 剩余 + DB order_info 下单数 = 初始库存 100
```

## 十一、常见问题

### Q1：压测时大量 500206 错误？

限流拦截器在工作，每个用户 5 秒最多 5 次。办法：增加用户数，或临时关闭限流：

在 `WebConfig.java` 中注释掉：
```java
// registry.addInterceptor(rateLimitInterceptor).addPathPatterns("/api/seckill/**");
```

### Q2：Token 为 null，秒杀请求报 500102？

登录没拿到 Token。检查：① `users.csv` 路径是否正确 ② 用户是否在 DB 中存在 ③ 密码是否对。

### Q3：JMeter GUI 卡顿？

GUI 模式本身消耗资源。正式压测用 CLI 模式（`-n` 参数）。

### Q4：RabbitMQ 消费者处理慢，队列堆积？

登录 http://localhost:15672 看 `seckill.queue` 的消息数。如果持续增长，增加消费者并发：

```yaml
# application.yml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 20   # 改大
```

### Q5：MySQL 连接池耗尽？

```yaml
# application.yml
spring:
  datasource:
    hikari:
      maximum-pool-size: 50  # 增大连接池
```

### Q6：想要更大并发，JMeter 本身扛不住怎么办？

用分布式压测：多台机器安装 JMeter，一台 Master + N 台 Slave，同时发请求。

```bash
# Master 节点（本机）
jmeter -n -t flashsale-load-test.jmx -R slave1_ip,slave2_ip -l result.jtl
```
